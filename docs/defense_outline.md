# 个性化法律工作台答辩提纲

## 1. 开场定位

建议先把产品定位讲清楚，再讲模型、图谱和工程实现。

可以直接这样概括：

> Legal Agent V3 不是单纯的律师软件，也不是普通聊天机器人。  
> 它面向普通用户和专业用户，既要能回答法律问题，也要能围绕具体案情做持续整理、追问和跟踪。

这里要强调三个使用层级：

- 纯法律问答：回答法条、程序、期限、标准
- 案情分析：围绕单次案情输入做分析和建议
- 持续跟踪：围绕同一案卷长期维护上下文、摘要和主体关系

这样老师会先明白：你做的不是“再做一个 RAG 聊天系统”，而是“把法律问答升级为个性化法律工作台”。

## 2. 核心问题定义

个性化法律工作台要解决的，不是单点问答，而是连续性、边界和可信性问题：

- 用户既会问“劳动合同法第八十七条规定了什么”，也会问“结合我这个案子，我下一步准备哪些证据”
- 如果系统把所有输入都静默写成结构化案情，会产生隐私和误写风险
- 如果系统只有 conversation，没有正式案卷对象，就无法稳定组织多轮、多会话的持续跟踪
- 如果图谱和主体同一性处理过于激进，就会把“我 / 公司 / 老板 / HR”误合并，反而降低可信度

因此，这条架构线的目标不是“让系统更聪明一点”，而是“让系统在个性化、持续化之后仍然可控、可解释、可答辩”。

## 3. H2-H4i 的架构演进故事

### 3.1 H2：先解决模式识别与用户同意

H2 的关键点不是模型能力，而是产品边界。

当前系统先区分四种模式：

- `LEGAL_QA`
- `CASE_ANALYSIS`
- `TRACKED_CASE`
- `UNKNOWN`

然后通过 `mode_consent_enabled` 控制是否进入用户确认流程。

这里最值得答辩时强调的是：

- `mode_consent_enabled` 默认是 `false`
- 这保证了旧客户端和 benchmark 完全兼容
- 新能力是增量开启，不会破坏既有路径

持久化语义也不是二元的，而是三态：

- `temporary`：保留普通消息，不写结构化案情和图谱
- `tracked`：允许持续跟踪和结构化持久化
- `unknown`：兼容旧客户端和旧 benchmark

一句话总结 H2：

> 先把“是否进入持续跟踪”讲清楚，再讨论“如何保存和利用这些数据”。

### 3.2 H3：把持续跟踪对象从 conversation 升级到 Dossier

如果只有 conversation，持续跟踪能力很快会失控，因为：

- 多个会话无法形成正式承载对象
- 摘要、状态、参与方信息没有稳定归属
- 前端也无法形成案卷入口和详情页

所以 H3 引入了 `Dossier`。

答辩时可直接强调三件事：

- `Dossier` 是正式案卷对象，不替代 conversation，而是聚合 conversation
- `Conversation.dossier_id` 让会话可以绑定案卷，也可以基于案卷新建 tracked 会话
- `summary + auto_summary` 双摘要并存，保证用户可控和系统整理能力同时存在

H3 的价值不是“多了一张表”，而是：

> 系统第一次具备了正式承载持续案情的对象，而不是把所有上下文都挤在单个 conversation 里。

### 3.3 H4：先做只读图谱聚合，而不是重写写入链路

图谱这一层的关键答辩点，不是“画了一个图”，而是“为什么只做 dossier 级只读聚合”。

当前 H4 的设计是：

- 底层 Neo4j 仍按 `conversation_id` 写入
- 不改写入 schema
- 不重构 `update_graph_task`
- 先通过 `GET /dossiers/{id}/graph` 聚合 dossier 绑定会话下的图谱数据

这有三个好处：

- 改动范围小，风险低
- 能快速形成 dossier 视角的图谱状态和预览
- 为 prompt 注入和前端解释能力提供稳定接口

这里的答辩语言可以非常明确：

> H4 不是激进地重做图数据库，而是在不破坏现有写入链路的前提下，先建立 dossier 级只读聚合层。

### 3.4 H4d-H4g：把图谱和主体信息变成 advisor 可读背景

H4d 以后，advisor 不只读 `dossier_context`，还读 `dossier_graph_summary`。

但要强调一个边界：

- 图谱摘要只作为案情背景
- 不作为法律依据
- 法律结论仍必须来自法律 RAG

H4g 则解决“案卷内主体如何稳定对齐”的问题。

这里不要讲成“系统会自动识别所有主体”，而要讲成：

- 系统只生成 candidate
- 用户确认后才形成 stable participant
- 不要求真实姓名
- 不让 LLM 静默猜身份
- 不跨案卷自动合并

这正是个性化工作台与普通法律聊天的重要差异：

> 不只是记住内容，还要记住谁是谁，但这个“谁是谁”必须由用户确认，而不是由模型臆断。

### 3.5 H4i：最后补数据库结构和删除一致性

H4i 不是新功能点，但它对答辩很重要，因为它说明这条线不是 demo 级拼装，而是考虑了长期运行稳定性。

这一步主要补了四件事：

- personalized workspace 相关表的索引补强
- runtime schema ensure 幂等，兼容旧库和新库
- conversation 删除/清空时清理 participant mentions
- dossier archive 仍保持软语义，不硬删历史关系数据

如果老师问“这些工作为什么要做”，可以直接回答：

> 因为当系统从普通问答升级成个性化工作台后，数据库已经不是只存聊天记录了，它开始承载案卷、主体、映射和摘要，schema 稳定性必须跟上。

## 4. 关键设计取舍

答辩时，这部分最容易形成技术说服力。

### 4.1 为什么 `mode_consent_enabled` 默认 false

- 因为必须先保住旧客户端和 benchmark
- 这说明新工作台能力是增量扩展，不是推倒重来

### 4.2 为什么 `temporary` 只阻止结构化持久化，不阻止普通消息保存

- 因为用户仍然需要正常聊天和查看历史
- 真正需要被 gate 掉的是结构化案情与图谱写入

### 4.3 为什么 Dossier 不直接替代 Conversation

- conversation 仍然是实际对话单元
- dossier 是持续案情的聚合单元
- 这是一种分层，而不是“所有信息重新塞进 dossier”

### 4.4 为什么 H4 只做只读图谱聚合

- 避免重写现有 Neo4j 写入模型
- 先把 dossier 视角读通，保证低风险可演示
- 后续如果需要 dossier-level write，再在 H5/H6 以后评估

### 4.5 为什么 participant resolution 放在 SQL 层

- 因为这本质上是“用户确认的身份 registry”
- 不是底层图谱实体自动合并问题
- SQL registry 更适合表达 confirmed participant 和 raw mention mapping

### 4.6 为什么不让 LLM 静默猜身份

- 法律场景里，身份误判的风险高于“不猜”
- “公司”“老板”“HR”“对方”在不同案卷里可能根本不是同一主体

### 4.7 为什么 graph 不能替代法律依据

- 图谱描述的是案情背景和结构化关系
- 法律结论仍必须回到法条、案例和 RAG grounding

## 5. 一句话答辩亮点

如果需要压缩成一句话，可以这样说：

> 语义检索解决“我该怎么办”；精确法条定位解决“第几条是什么”；  
> Dossier 解决“这个案子跟到哪了”；participant resolution 解决“我 / 公司 / 老板是不是同一主体”。

如果需要再压缩成两个关键词：

- 可持续跟踪
- 可控个性化

## 6. 建议演示路径

建议按“从可靠问答，到持续工作台”的顺序演示。

### Demo 1：纯法律问答不污染案情图谱

输入：

`劳动合同法第八十七条规定了什么？`

要点：

- 命中 exact law article lookup
- 走 `GENERAL_CONSULT`
- 不触发 fact_updater
- 不触发 graph update
- 回答直接给出第 87 条含义

这一段用来说明：系统不会把纯法条问答错误写成用户案情。

### Demo 2：tracked onboarding 与 Dossier 创建

输入一段真实案情描述，选择“保存并持续跟踪”。

要点：

- 先经过 mode consent
- 再进入案卷初始化
- 确认案卷名称与 participant aliases
- 会话绑定 dossier

这一段用来说明：系统不是静默记忆，而是显式进入持续跟踪。

### Demo 3：案卷详情、摘要与图谱状态

打开 dossier 详情。

要点：

- 可以看到绑定会话列表
- 可以看到手动摘要和自动摘要
- 可以看到图谱状态和图谱预览
- 可以看到 participant aliases / confirmed participants

这一段用来说明：持续跟踪对象已经从 conversation 升级成案卷工作台。

### Demo 4：案卷追问只回答，不误写图谱

输入：

`结合这个案卷，我接下来申请劳动仲裁时应该准备哪些证据？`

要点：

- 不再弹 mode consent
- 不再当作 case fact update 写图谱
- advisor 直接回答证据清单

这一段说明：系统能区分“事实补充”和“围绕案卷的咨询追问”。
