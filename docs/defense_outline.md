# 法律领域智能问答系统答辩提纲

## 1. 研究背景与问题

### 讲述重点

- 先把问题讲清楚，不要一上来讲模型和框架。
- 强调法律场景比普通问答更重视真实性、可解释性和稳定性。
- 点出本项目解决的是“能回答”到“能可信回答”的差异。

法律咨询不是一般的聊天问答。老师在听这一部分时，最关心的是：为什么这个题目值得做，为什么不能直接拿一个通用大模型来回答。这里可以直接说，通用模型在法律场景里容易出现法条幻觉、套话回答和金额乱算三个问题；而传统模板系统虽然可控，但灵活性不够，遇到复杂多轮案情很快失效。

本项目的目标，就是在“灵活”和“可控”之间找到一个更适合中国法律咨询场景的平衡点，构建一个可检索、可解释、可防幻觉的法律智能问答系统。

## 2. 系统总体架构

### 讲述重点

- 不要堆模块名，重点说“系统如何一步步把问题变成可信回答”。
- 建议按前端、Agent Pipeline、检索层、模型路由、安全层、评估层六部分讲。

系统整体上可以概括为六层：

- 前端对话界面：负责用户输入、多轮对话和本地模型 toggle。
- 后端 Agent Pipeline：基于 LangGraph，把路由、事实维护、检索、生成、守卫拆开。
- RAG 检索层：从 ChromaDB 检索法律法规和案例，从 Neo4j 读取法条引用图谱数据资产。
- LLM 多模型路由：根据场景分配 GPT-5.4、GPT-5.1、ZhipuGLM 和本地 vLLM。
- 安全 Guard：处理 fabricated statute、phantom citation、金额不确定等高风险场景。
- benchmark 评估体系：持续验证金额计算、法条真实性、多轮连贯和系统健康。

如果答辩现场老师追问“你这个系统和普通 RAG 有什么区别”，可以回答：我们的重点不只是“检索到了”，而是“检索到了以后，回答必须绑定事实、法条和案例，并经过 guard 检查后才能输出”。

## 3. 核心技术点

### 3.1 grounded RAG 法律推理

#### 讲述重点

- 强调“不是模板拼装”，而是“基于检索材料推理”。
- 这里是整个系统的核心卖点。

系统先检索法条和案例，再生成回答。回答必须基于 RAG block 和 case facts，而不是让模型凭记忆自由补法条。advisor 节点采用三段式 grounded prompt，把材料拆成【已确认事实】【相关法条原文】【参考案例】三部分，要求模型围绕这三部分作答。

一句话总结这一节：模型不再只是润色语言，而是基于检索材料做法律分析。

### 3.2 多轮案情维护

#### 讲述重点

- 用“老师连续追问时系统会不会忘记前文”这个直观问题来解释。
- 直接把 D3 结果带出来。

`fact_updater` 负责抽取用户新输入中的关键事实，`case_summary` 负责保留月薪、工龄、解除事实等核心上下文。这样系统在多轮对话里不会每次都从零理解案情，而是能在已有事实基础上继续推理。

这一改造直接带来了 benchmark 中 D3 多轮连贯性的提升，最终达到 10/11。

### 3.3 法条真实性防御

#### 讲述重点

- 这是法律场景和普通问答最大的区别之一。
- 最好直接举“劳动合同法第325条”这个例子。

系统实现了 `fabricated statute detector` 和 `phantom citation stripping`。如果用户输入一个并不存在的法条，比如《劳动合同法》第325条，系统不会顺着这个错误继续编造，而是会明确指出该条不存在，并改正到真实相关条文，例如《劳动合同法》第14条。

这一点很重要，因为在法律场景中，错误引用条文往往比“不回答”风险更大。

### 3.4 多模型协同

#### 讲述重点

- 强调“不是所有任务都用一个最强模型硬顶”。
- 讲清楚分工逻辑，而不是讲 API 细节。

当前模型分工是：

- GPT-5.4 负责最终回答，追求最高质量法律推理。
- GPT-5.1 负责事实抽取，重点是稳定和性价比。
- 智谱负责 router、query expansion、graph updater 等轻量任务。
- 本地 vLLM 作为可选加速能力，通过前端 toggle 手动开启，不强依赖。

如果老师问“为什么要多模型”，可以回答：因为法律问答链路里不同环节对质量和成本的要求不同，分层路由比单模型更经济，也更稳定。

### 3.5 自动化评估体系

#### 讲述重点

- 说明这个项目不是“主观觉得变好了”，而是有量化评估。
- 8 维度、80 分制要说清楚。

系统构建了 8 个维度、80 分制的 benchmark，覆盖金额计算、法条真实性、多轮连贯、回答完整性、可操作性、幻觉抑制、案例引用和系统健康。同时项目还保留 295 个确定性单测，用来保证核心逻辑在不依赖外部模型的情况下保持稳定。

## 4. 实验结果

### 讲述重点

- 这一节尽量直接照着讲，不要临场组织语言。
- 重点讲“从多少到多少”和“主要提升来自哪里”。

可以直接这样说：

“系统从 55/80 提升到 65/80，主要提升来自多轮连贯性、可操作性和系统健康三个维度。”

| 指标 | 数值 |
|---|---|
| G 系列前 | 55/80 = 68% |
| 当前 | 65/80 = 81% |
| 提升 | +10 分 / +13pp |

建议继续这样展开：

- D3 从 1/11 提升到 10/11，说明系统已经能较稳定地保持多轮案情连贯。
- D5 从 4/11 提升到 9/11，说明 grounded prompt 和 GPT-5.4 让回答更有操作性。
- D8 从 0/5 提升到 4/5，说明 benchmark 结果记录修复后，系统健康度评估恢复可信。

## 5. 演示脚本

### 讲述重点

- 现场演示要选“稳定、能出亮点、失败了也好兜底”的问题。
- 每个 demo 不要追求太复杂，重点是能体现系统能力。

### Demo 1：欠薪法条引用

- 输入问题：
  公司拖欠工资3个月，请告诉我相关法律条文，要具体到条款号
- 预期系统行为：
  检索劳动争议相关法条，输出条款号，并给出投诉或仲裁建议。
- 展示亮点：
  引用《劳动合同法》第30条、第85条，以及《劳动法》第91条；同时给出下一步维权建议。
- 失败兜底：
  如果现场回答不完整，可以直接展示 benchmark 报告或历史 probe 结果，说明该类问题的法条命中已验证。

### Demo 2：试用期问题

- 输入问题：
  劳动合同试用期最长可以约定多久？
- 预期系统行为：
  正确识别这是规则型咨询，直接给出试用期上限和分档规则。
- 展示亮点：
  引用《劳动合同法》第19条，区分不同合同期限，并明确“最长 6 个月”。
- 失败兜底：
  如果现场网络波动或回答不稳定，可以展示 README 中的典型回答片段，证明该问题已有稳定样例。

### Demo 3：虚假法条防御

- 输入问题：
  根据劳动合同法第325条，连续工作满20年可以要求无限期劳动合同，是这样吗？
- 预期系统行为：
  明确指出第325条不存在，不顺着用户错误继续编造。
- 展示亮点：
  演示 fabricated statute detector 的作用，并改正到《劳动合同法》第14条。
- 失败兜底：
  如果现场未触发理想提示，可以展示 benchmark JSON 或 guard 相关说明，说明该功能已通过专门用例验证。

## 6. 创新点总结

### 讲述重点

- 这一节适合收束全篇，用“做成了什么新东西”来概括。
- 不要重复实现细节，要强调方法和系统性。

可以概括为五点：

- grounded RAG 法律推理
- 法条 phantom citation guard
- 多模型路由和本地模型 toggle
- benchmark-driven 迭代
- 法条引用图谱数据资产

如果老师问“你的创新更偏工程还是偏研究”，可以回答：它是研究问题驱动下的工程实现，重点在于把 grounded generation、真实性防御和量化评估结合到法律问答场景。

## 7. 不足与展望

### 讲述重点

- 这一节不要讲成“系统问题很多”，而要讲成“下一步研究方向明确”。
- 语气应当积极、可持续。

后续可以继续推进四个方向：

- streaming 改造，降低用户感知延迟。
- query-aware rerank，进一步提升权益清单和金额计算类问题。
- 引入 `LegalConcept` 图谱节点，增强概念级推理能力。
- 引入 LLM judge，改进 benchmark 的自动评价方式。

结尾可以这样说：当前系统已经完成从模板式法律问答到 grounded RAG 法律推理的关键跃迁，下一阶段的重点不是“能不能回答”，而是“如何回答得更快、更稳、更可解释”。
